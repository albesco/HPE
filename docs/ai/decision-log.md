# Decision Log

Format:
- YYYY-MM-DD | Area | Decision | Reason | Consequences

- 2026-05-13 | Detection pipeline | Add a separately trained YOLO one-class `swimmer` detector before VitPose++ | GT bbox evaluation overestimates real inference quality; YOLO should provide bboxes for the top-down pose model | YOLO training is prepared from GT bbox annotations in a dedicated `script/yolo_training/` workflow; future VitPose++ evaluation should compare GT bbox vs YOLO bbox pipelines.
- 2026-05-13 | Dataset bbox convention | Store Side_above_water GT bboxes with `0.10` padding in the prepared VitPose++ dataset and keep YOLO conversion padding at `0.0` | Original GT bboxes were visually too tight; adding padding once makes YOLO and VitPose++ train on the intended margin while avoiding double expansion | Regenerate dependent YOLO datasets after VitPose++ dataset regeneration; YOLO-predicted bboxes should be passed downstream as-is unless a new padding convention is deliberately trained and evaluated.
- 2026-05-14 | Dataset bbox convention | Increase Side_above_water prepared GT bbox padding from `0.10` to `0.20` | Visual inspection indicated bboxes should be less tight before both YOLO and VitPose++ training | VitPose++ train/val/test and the derived YOLO dataset were regenerated; YOLO conversion still uses `bbox_padding_ratio=0.0` to avoid double padding.
- 2026-05-14 | Dataset bbox convention | Use anisotropic GT bbox padding: horizontal `0.20`, vertical `0.25`, minimum `15 px` per side | The swimmer needs more vertical context while retaining controlled horizontal expansion | Preparation scripts now default to anisotropic padding; regenerate VitPose++ and derived YOLO datasets before the next training run.
- 2026-05-14 | VitPose++ training observability | Add an optional current-status text file updated during training | Long-running tmux jobs need a quick progress check without parsing logs or attaching to the session | `src/vitpose_base/tools/train.py` accepts `--status-file` and `--status-interval`; the hook overwrites one status file with current epoch, iteration, percent, ETA, and work dir.
- 2026-05-20 | SwimXYZ visibility semantics | Treat SwimXYZ `z` as a 3D coordinate, not as keypoint visibility/confidence | The active conversion pipeline documents `z` as a Blender-space coordinate and reconstructs COCO/MMPose visibility from image position instead of consuming `z` | In the prepared pipeline, visibility is currently collapsed to `v=0` for missing/border-clamped points and `v=2` for retained points; `v=1` occlusion is not preserved unless a separate source field is introduced.
- 2026-05-15 | VitPose++ checkpoint policy | Keep only latest periodic checkpoint plus best validation checkpoint | Each VitPose++ checkpoint is about 11 GB, so retaining every epoch is too expensive while best/latest are enough for resume and model selection | Launchers/config generation use `checkpoint_config.max_keep_ckpts=1`, `create_symlink=True`, and `evaluation.save_best='AP'`.
- 2026-05-15 | VitPose++ resume robustness | Ignore invalid checkpoint metadata config during resume while still loading model/optimizer/epoch state | A resumed checkpoint contained an unparsable `meta.config`; failing only on metadata blocked otherwise valid incremental training | `runner.resume` is wrapped so invalid metadata config is tolerated; future resume tests should still verify model state and metrics continuity.

- 2026-05-16 | VitPose++ checkpoint policy | Keep best validation checkpoint plus the latest three periodic checkpoints (max_keep_ckpts=3) | Continuing beyond epoch 30 may overfit, so training needs a small rollback window without retaining every 11 GB checkpoint | Future launchers/config generation preserve best_AP_*.pth, latest.pth, and the two previous periodic checkpoints while deleting older periodic checkpoints.
- 2026-05-20 | YOLO+VitPose++ pipeline | Consolidate on `YoloVitPose_mAP` with `script/yolo_training/evaluate_yolo_vitpose_map.py` and MMPose-only predicted skeleton visualization | Previous saved YOLO+VitPose keypoints were not reproducible despite identical YOLO bboxes; the current pipeline correctly converts YOLO `xyxy` to COCO `xywh` and lets MMPose perform the top-down crop/affine | Old failed artifacts and custom/mixed visualization scripts were removed; full-test mAP must be regenerated before reporting end-to-end metrics.
